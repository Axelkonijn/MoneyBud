# 5. Building Block View

**What belongs here:** The static structure, decomposed in levels. Level 1 is the whitebox view of
the whole system — its top-level parts and their responsibilities. Deeper levels zoom into any
part that is complex enough to warrant it.

Only decompose where it earns its keep. A level-3 breakdown of a trivial component is noise.

---

MoneyBud is **four source projects and one test project**. Until the fifth increment it was one
library and one test project. The UI split into a layer that decides what the screen shows and a
thin one that draws it. The reasoning is in [ADR 0006](../decisions/0006-three-source-projects.md),
which supersedes the "two projects" of [ADR 0004](../decisions/0004-solution-layout.md). The
persistence increment added the fourth, `MoneyBud.Storage`, which keeps the ledger in a file
([ADR 0007](../decisions/0007-keeping-the-ledger.md), which amends 0006). This section stays short,
for the same reason [§7](07-deployment-view.md) is.

**A phone head is settled, not built** (2026-09-29, [ADR 0013](../decisions/0013-an-android-phone-app.md)).
It will be a second thin Avalonia head beside `MoneyBud.Desktop`, over the same domain, presentation
layer and storage, and held to the Desktop's rule: it decides nothing. **Which projects it needs, and
what they are called, are left to this increment's plan**, so the diagram below does not draw it yet.
The one thing it has that the Desktop has not is themes, which change only how MoneyBud looks.

## Level 1 — Whitebox: MoneyBud

```
MoneyBud.Desktop ─────► MoneyBud.Presentation ─────► MoneyBud.Domain
   (Avalonia)              (no UI toolkit)           (base class library only;
       │                                              defines ILedgerStore)
       │                                                     ▲
       └──────────────► MoneyBud.Storage ────────────────────┘
                          (no package)

MoneyBud.Specs ─────► Presentation, Domain and Storage   (never the Desktop)
```

An arrow is a project reference. The Desktop references the Presentation layer and Storage. The
specs reference Presentation, Domain and Storage. Nothing references the Desktop. **The presentation
layer does not reference Storage.** It knows a store only through `ILedgerStore`, which the domain
defines and `MoneyBud.Storage` implements, and the Desktop is the one place that puts the two
together.

| Building block | Responsibility |
|---|---|
| **`src/MoneyBud.Domain`** | The model and its rules. Categories, budgets, expenses, income, budget periods and the `Money` type. Adds and archives categories and brings archived ones back, under one category name rule (`CategoryName`). A `Category` is a class **with identity**, one instance per category, whose name only the domain can set. So it can be renamed (`Ledger.RenameCategory` → `RenameCategoryResult`, with `RenameOutcome` and `RenameRefusal`), and one with no history anywhere can be deleted (`Ledger.CanDelete`, `Ledger.DeleteCategory`). Ships the six default categories for a first start (`Ledger.StartNew`). Assigns to categories (`Ledger.Assign`), which is the only way a budget is made. Records expenses and incomes, each with a ledger-issued `Id`, and changes them in place (`ChangeExpense` → `ChangeExpenseResult`, `ChangeIncome` → `ChangeIncomeResult`, both with `ChangeOutcome`) or removes them (`RemoveExpense`, `RemoveIncome`), judging a change by recording's own checks. Computes *Remaining*, *Unassigned* and whether a period is *Over-assigned*, decides what to refuse, and reports what each act did. Decides which categories a period shows (`Ledger.CategoriesShownIn`). **Since the opening-a-period increment** it also works out the plan a period is offered, afresh on every call and never stored (`Ledger.PlanOfferedIn` → `PlanOffer`: the source period, one `PlanFigure` per category in the plan, `Total` and `FigureFor`), and takes it over (`Ledger.TakeOverPlan` → `TakeOverPlanResult`) by calling `Assign` once per figure, so `Assign` stays the only writer of a budget. Since the persistence increment it also defines **what is kept and the port it is kept through**, without knowing what a store is made of: `LedgerSnapshot`, the whole ledger as plain data, with categories referred to by a key rather than a name; `Ledger.ToSnapshot` and `Ledger.FromSnapshot`, the second re-checking every rule the running ledger keeps and throwing `InvalidDataException` for kept data that breaks one; and `ILedgerStore`, with its `Claim` and `LoadResult`. **Since the accounts increment** it holds the location dimension ([ADR 0008](../decisions/0008-balance-is-worked-out.md)). `Account` has identity and no balance. `Transfer` and `BalanceCorrection` implement `IEntry` with `Expense` and `Income`, and all four share one id counter. The acts are `Ledger.AddAccount`, `RenameAccount`, `CanDeleteAccount`, `DeleteAccount`, `MakePool`, `RecordTransfer`, `ChangeTransfer`, `RemoveTransfer`, `CorrectBalance` and `RemoveBalanceCorrection`, with their result types in `AccountResults` (`AddAccountResult` with `AccountRefusal`, `RenameAccountResult`, `RecordTransferResult` and `ChangeTransferResult` with `TransferRefusal`, and `CorrectBalanceResult`). `BalanceOf`, `NetWorth`, `IsOverdrawn`, `DifferenceOf` and `HistoryOf` work figures out on every call and store none. `Accounts` lists the pool account first. Every expense and income is on an account, and the constructor takes the pool account's name; `StartNew` names it *Betaalrekening*. **Since the backing increment** it holds where the two dimensions meet ([ADR 0009](../decisions/0009-movements-are-entries.md)). `Movement` is a fifth `IEntry`, money MoneyBud moved for a category, with a `MovementReason` and a `MovementDirection`. `Backing` is a category's account and two `EntryMark`s, and `EntryMark` is the one "after this" rule, shared with a balance correction's holding. `Ledger.SetBacking` → `SetBackingResult` (with `BackingOutcome`) backs, re-points or unbacks. `Assign` also moves money for a backed category in the current period. `Ledger.Settle` writes the money planned for periods that have begun, and every act that changes the ledger calls it first. `BackingOf`, `ThereFor` and `AccumulatedFor` are worked out on every call. **Since the sweep increment** ([ADR 0010](../decisions/0010-sweeps-and-period-ends.md)) `Movement` has a fifth reason, `Swept`, and `SweptFor`, the period a sweep was for. `Ledger.Settle` also records each period's end, the categories backed at that moment, and sweeps it before moving the new period's planned money. The sweep's queries and acts are `SweepDestination`, `SweepDestinationChoices`, `SetSweepDestination` → `SetSweepDestinationResult` (with `SweepDestinationOutcome`), `PeriodLeftover`, `SweepLineFor` → `SweepLine` (with `SweepLineKind` and `SweptPart`), `BringUpToDate` → `BringUpToDateResult`, and `TakeSweepsMade` → `SweepMade`, the sweeps settling made, to be announced once; the types are in `Sweep.cs`. `LedgerSnapshot` gains the destination, the period-end records and the amounts let go. **Since the recurring-entries increment** ([ADR 0011](../decisions/0011-recurring-entries.md)) `Recurring.cs` holds `Frequency` (`Weekly`, `Monthly`; one-off is `null`, the absence of a repeat), `RecurringEntry`, the internal state a repeat keeps beside its occurrences (their ids, the frequency, the day a monthly one was last set to, the next date), and `OccurrenceMade`, an occurrence to be announced with the category it brought back. `RecordExpense` and `RecordIncome` take a `Frequency?`, and `ChangeExpense` and `ChangeIncome` gain an overload that takes one; the overload without it keeps the frequency as it is. `Ledger.FrequencyOf` gives the frequency of the latest occurrence of a running repeat and null for every other entry, and `Ledger.SetsTheRepeat` says whether an entry's frequency can be changed. `Ledger.Settle` works event by event and records the occurrences that are due, and `TakeOccurrencesMade` hands them over once. `LedgerSnapshot` gains `Repeats`, as `RepeatSnapshot`s. **Since the start-day increment**
([ADR 0012](../decisions/0012-the-calendar-is-a-history.md)) `BudgetPeriodCalendar` is a **history of
changes**: a start day since always and a list of `StartDayChange(PeriodFrom, From, StartDay)`, immutable,
with `StartDay` (the day now set), `ChangedFrom` (a new calendar with a change made) and `FromChanges`
(a kept history rebuilt, and refused if impossible). `Ledger.ChangeStartDay` → `ChangeStartDayResult`
(`Day`, `WasChanged`, `Current`, `Ended`) changes it, re-keying plans made ahead and, when it ends the
current period, passing into the next dated today; `Ledger.PreviewStartDay` gives the same answer
without acting. `Backing` gains `AccumulatingFrom` and `HereFrom`, the first day of the period each mark
was set in. `LedgerSnapshot` gains the calendar's changes. A ledger always begins on the 1st: the
constructor, `StartNew` and `FromSnapshot` no longer take a calendar. Depends on nothing but the .NET base class library: no UI framework, no file handling, not even an ambient clock (`TimeProvider` is passed in) |
| **`src/MoneyBud.Presentation`** | **Everything the screen decides, with no UI toolkit.** `MoneyBudApp` is the whole screen: the period on screen and stepping, the acts the user can take with their defaults, and the notice afterwards, including where an entry went when it landed in another period. Since the corrections increment it also holds the one question MoneyBud asks, whether to remove an entry (`Question`, `Confirm`, `Decline`), and the category being renamed. The expense and income forms have a *Wijzigen* state for an entry loaded from its row, and the rows carry their entries. `PeriodOverview` is one period as the Overview shows it (rows, markers, the two lists), and `Ring` is its slices with their clockwise shares, each at least `Ring.MinimumSweep`. `MoneyBudApp.PointAt` and `Ring.SliceAt` decide which slice is pointed at and what the ring's hole shows. **Since the opening-a-period increment** `PeriodOverview` also carries the plan offered (`Offer`, `HasOffer`, and `OfferText` for the button), each `CategoryRow` its grey figure (`PlanFigure`, `PlanText`), and the rows sort by *Budget*, then plan figure, then order added. `MoneyBudApp.TakeOverPlan`, bound as `TakeOverCommand`, takes the plan over into the period on screen and says which period it went into. It also holds the category suggestions, the entry forms, `AmountInput` for reading typed text, and `Tekst` for every Dutch word shown. **Since the persistence increment it decides everything about keeping data that the user meets**: `MoneyBudStart.Start` claims and loads a store and returns the screen or the one reason MoneyBud does not start (`StartResult`, `StartRefusal`); `MoneyBudApp` saves after every act that changed the ledger, holds the save line (`IsUnsaved`, `SaveLine`), retries on `Tick` and makes the last attempt on `Close`. It knows a store only through the domain's `ILedgerStore`. **Since the accounts increment** it holds the strip, as one `AccountLine` per account with its balance, pool flag and marker, plus `NetWorth` with its marker. It holds `AccountChoices`, the forms' account lists, which get a new collection only when the accounts change. It holds two small forms: `AccountForm` for adding, and `TransferForm`, with its own *Wijzigen* state. The expense and income forms gain an account (`ChosenAccount`). **The history state is in `MoneyBudApp`**: `HistoryAccount`, `History` as `HistoryLine`s with each balance correction's difference, the balance box, renaming the account, and whether it can be deleted or made the pool. **Since the backing increment** each `CategoryRow` carries its *Staat op* list (`BackingChoices` of `BackingChoice`, `ChosenBacking`) and its *Opgebouwd* (`Accumulated`, `AccumulatedText`, `AccumulatedMarker`). `MoneyBudApp.SetBacking` announces what moved, and says nothing for the backing already set. `MoneyBudApp` settles when it is made and on every `Tick`, and keeps what moved. `ExpenseForm.ChosenAccount` follows the category typed until an account is picked. `HistoryLine` shows movements, read-only. **Since the sweep increment** `PeriodOverview` carries the *Restant naar* list in the current and later periods (`ShowsSweepDestination`, `SweepChoices` of `SweepChoice`, `ChosenSweepDestination`) and an ended period's line (`SweepLine`, `SweepLineText`, `SweepLineMarker` with the badge *Tekort*, `CanBringSweepUpToDate`). `MoneyBudApp.SetSweepDestination` announces a choice and does nothing at all for the one already set, and `BringSweepUpToDate`, bound as `BringUpToDateCommand`, acts on the period on screen. After every act, on start and on every `Tick`, `MoneyBudApp` takes the sweeps settling made, says them first and keeps the ledger straight away. **Since the recurring-entries increment** the expense and income forms end with a *Herhalen* list (`FrequencyChoices` of `FrequencyChoice`, `Frequency`, `ChosenFrequency`, `CanChangeFrequency`), which a form in *Wijzigen* re-reads on every redraw, so an entry that stops being the latest while open locks there. `ExpenseLine` and `IncomeLine` carry `RepeatLabel`, the grey *maandelijks* or *wekelijks* on a latest occurrence's row; `HistoryLine` has none. `Notice.Repeated` lists the occurrences a notice names. `MoneyBudApp` takes the occurrences wherever it takes sweeps, keeps them straight away, and says them in the order they happened: for the four entry acts, `SettleBeforeActing` holds what settling did before the act, so that goes in front of the act's sentence and what the act itself caused after it. **Since the start-day increment** `MoneyBudApp` holds the *Periode begint op* list: `StartDayChoices` (1 to 31), `StartDayChoice` (an `int?`, null ignored and safe to write back), `StartDayShownIn(period)` (null on a past period; the day set, or the day asked about while the question waits), `ShowsStartDay` and `ChooseStartDay`, which asks. `Question` gains `ConfirmText`, *Verwijderen* or *Wijzigen*, so there are two kinds of question and still one at a time; the tick drops a start-day question when the day has changed. Confirming moves `ShownPeriod` and `AssignForm.Period` to the period nearest to where each was. `Tekst.PeriodName` has five forms and its own short months, and `HistoryLine.SweptPeriod`, filled by `MoneyBudApp.History`, names a sweep's period through the ledger's calendar, so `Tekst` no longer makes a default calendar. References the domain, and CommunityToolkit.Mvvm, which depends on no toolkit ([ADR 0005](../decisions/0005-avalonia-ui-toolkit.md)) |
| **`src/MoneyBud.Storage`** | **Where the ledger is kept, and in what form** ([ADR 0007](../decisions/0007-keeping-the-ledger.md)). `FileLedgerStore` implements `ILedgerStore` on one folder: it claims `moneybud.lock` exclusively, loads `moneybud.json`, and saves by writing `moneybud.json.tmp`, flushing it and renaming it over the data file. `FileLedgerStore.DefaultFolder` is the user's local application data plus `MoneyBud`. `LedgerJson` writes and strictly reads the format: whole cents as integers, `yyyy-MM-dd` dates, a format name and version. **Version 2 since the accounts increment**, with accounts, the pool account, an account on every expense and income, transfers and balance corrections, and still no balance. Version 1 is refused ([ADR 0008](../decisions/0008-balance-is-worked-out.md)). **Version 3 since the backing increment**, adding a backing on each category, the movements and `settledThrough`. Versions 1 and 2 are refused ([ADR 0009](../decisions/0009-movements-are-entries.md)). **Version 4 since the sweep increment**, adding `sweptFor` on each movement, `sweepDestination`, `periodEnds` and `letGo`. Versions 1 to 3 are refused ([ADR 0010](../decisions/0010-sweeps-and-period-ends.md)). **Version 5 since the recurring-entries increment**, adding `repeats`. **Version 4 is read**, as data with no repeats; a version-4 document that has a `repeats` list is refused, and versions 1 to 3 still are ([ADR 0011](../decisions/0011-recurring-entries.md)). **Version 6 since the change to *Opgebouwd*** (2026-09-28), adding `notMovedCents` and `paidHereBeforeCents` to a backing. **Version 5 is read**, and the two figures worked out again from the order entries were recorded in ([§12](12-glossary.md), *Backing a category that already has money*). **Version 7 since the start-day increment**, adding a `calendar` list (`periodFrom`, `from`, `startDay`; empty when never changed) and a backing's `accumulatingFrom` and `hereFrom`. **Versions 6, 5 and 4 are read**, version 6 as a calendar never changed; any of them carrying a `calendar` is refused ([ADR 0012](../decisions/0012-the-calendar-is-a-history.md)). Decides nothing the user sees. References the domain only, and no package |
| **`src/MoneyBud.Desktop`** | The Avalonia window, laid out income, plan, expenses, and `RingControl`, which draws the ring from `Ring`'s shares and turns the pointer's position into a share. Transaction rows are buttons that load their entry, and each category row has its acts in a line under its name. The button that takes a plan over sits directly under the assign form and is visible only while `HasOffer`; the grey plan figure sits under each row's *Budget* figure, in the same column. At start it makes a `FileLedgerStore` on the default folder and hands it to `MoneyBudStart`, then shows either the window or a small message window with the refusal's text. It calls `MoneyBudApp.Tick` once a minute and `Close` when the window closes. **Since the accounts increment** it also draws the strip across the top, the two small forms under it, the history panel under the strip at full width (closed with *Sluiten*), and the account lists as `ComboBox`es. The ring's minimum height is 180. **Since the backing increment** each category row has a compact *Staat op* `ComboBox` beside *Hernoemen*, *Opgebouwd* is a caption under the row's figures and in the ring's hole, and movement rows appear in the history. **Since the sweep increment** a line directly under the ring holds the *Restant naar* `ComboBox` in the current and later periods, or, in an ended period, the line's text, the marker with *Tekort* and the *Restant bijwerken* button. **Since the recurring-entries increment** the expense and income forms end with the *Herhalen* `ComboBox`, its caption to the left of the list, enabled by `CanChangeFrequency`, and a row's account name and grey repeat label sit side by side on one caption line. **Since the start-day increment** a *Periode begint op* `ComboBox`, with its caption, stands to the right of the period name and its step buttons, visible on `ShowsStartDay`, and the question's confirming button binds `Question.ConfirmText`. **Deliberately thin, and with no automated tests except two that read the window's markup as text**: the order of the form fields, now including the account list last and the transfer form's order, and the save line standing beside the notice and the question ([§8.4](08-crosscutting-concepts.md), [§11](11-risks-and-technical-debt.md)) |
| **`tests/MoneyBud.Specs`** | Runs the specification: Reqnroll step definitions on xUnit, with the scenario's world in `Support/`. *Given* steps set up the ledger; every *When* acts through `MoneyBudApp`; *Then* steps about what is shown read the presentation layer ([§8.4](08-crosscutting-concepts.md)). The sweep's steps are in `SweepSteps`, the recurring entries' in `RecurringSteps`, and the start day's in `StartDaySteps`. **Every scenario keeps its data through the real `FileLedgerStore`**, in a temporary folder of its own. Also holds the developer unit tests in `Unit/`, for the domain, the presentation layer and storage. They are tests and not specification; ADR 0004 says why they share a project and what rule keeps them subordinate |

`features/` is **not a building block.** It holds the Gherkin specification, and the specs project
*links* those files in rather than owning a copy of them (ADR 0004). It is listed here only because
a reader looking at the solution will see the linked files and wonder where they really live.

The solution file is `MoneyBud.slnx` at the repository root.

## There is no level 2

None of the four projects has an internal boundary worth drawing. The domain is a handful of types,
and [§8.1](08-crosscutting-concepts.md) says what is worth saying about them. The presentation layer
is a handful more, and [§8.4](08-crosscutting-concepts.md) does the same for it. Storage is two
classes, and [§8.3](08-crosscutting-concepts.md) and ADR 0007 say what matters about them. The
Desktop is one window and one control. A breakdown of any of them would restate the class list. The
code itself is the level-2 view.

Adding a capability therefore updates the responsibilities above and §8, and leaves the rest of this
section alone. The income, category and assigning increments each added types to the domain and
moved no boundary. The UI increment was the first that did move them, and ADR 0006 records it. It added
two queries to the domain, `CategoriesShownIn` and `ExpensesIn`, and no behaviour. The corrections
increment moved none either. It added acts and result types to the domain, and gave `Category` and
the entries identity, which is a change inside the domain and is described in
[§8.1](08-crosscutting-concepts.md). The persistence increment moved a boundary again, the second
increment to do so. It added `MoneyBud.Storage`, and a port and a snapshot to the domain
([ADR 0007](../decisions/0007-keeping-the-ledger.md)). The opening-a-period increment moved none. It
added a query, an act and their two types to the domain, and to the presentation layer the offer on
the Overview and the act behind its button. Storage did not change, because nothing new is kept: the
offer is worked out from the budgets already stored. **The accounts increment moved none either.** It
added the location dimension inside the domain, the strip, forms and history to the presentation
layer, and a second version of the file format to storage
([ADR 0008](../decisions/0008-balance-is-worked-out.md)). Every project kept its references.
**The backing increment moved none either.** It added movements, backing and settling inside the
domain, the *Staat op* list and *Opgebouwd* to the presentation layer, and a third version of the
file format to storage ([ADR 0009](../decisions/0009-movements-are-entries.md)). Settling is the
first thing MoneyBud does when a period begins rather than on request, and it runs inside the domain
and on the presentation layer's existing tick. It needed no new block. **The sweep increment moved
none either.** It added the sweep to settling and its queries and acts to the domain, the list, the
line and the button to the presentation layer, and a fourth version of the file format to storage
([ADR 0010](../decisions/0010-sweeps-and-period-ends.md)). Every project kept its references.
**The recurring-entries increment moved none either.** It added recurring entries and settling event by
event to the domain, the *Herhalen* list, the grey label and the occurrences' notice to the
presentation layer, and a fifth version of the file format to storage
([ADR 0011](../decisions/0011-recurring-entries.md)). Every project kept its references. **The
start-day increment moved none either.** It made the calendar a history and added one act to the
domain, the list, the second kind of question and the period names to the presentation layer, and a
seventh version of the file format to storage ([ADR 0012](../decisions/0012-the-calendar-is-a-history.md));
the sixth, from the change to *Opgebouwd*, moved nothing. Every project kept its references.

## What used to be absent

Until the persistence increment this section had a table of one: **anything that stores data**,
absent for a recorded reason. [§8.3](08-crosscutting-concepts.md) deferred persistence with a
trigger, and the section named adding a store as the moment to re-examine the project layout. The
trigger never fired. The stakeholder chose to build persistence anyway, on 2026-09-26, and the
re-examination produced the fourth project above rather than a store folded into an existing one
(ADR 0007 says why). Nothing else is conspicuously absent from the structure. What the model lacks
is absent from the domain, and §8.1 lists it. Accounts were on that list until the accounts
increment, backed categories until the backing increment, the sweep until the sweep increment,
recurring transactions until the recurring-entries increment, and changing the period start day,
briefly, until the start-day increment. What is left on it is deliberately never coded.

[§7](07-deployment-view.md) maps all of this onto one process on one machine, which no part of
this section changes.
