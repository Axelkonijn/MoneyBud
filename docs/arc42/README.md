# Architecture Documentation — arc42

MoneyBud's architecture documentation, following the [arc42](https://arc42.org) template.

## How to read this

Sections are filled in **progressively**, not all at once. An empty section is normal and means
"we haven't needed to decide this yet" — it is not a gap to be padded out. arc42 is explicit about
this: write what carries information, leave the rest.

Each file states what belongs in it, so it's clear what's missing versus what's deliberately
still open.

The **category model** is settled and now **built**: names trimmed at the ends, compared case-insensitively with any run of inner whitespace counting as one space, and stored as typed (a correction, since made, to code that compared them exactly by accident), with a name that trims to nothing refused; adding an existing name hands back the existing category **with its existing spelling** and says so; removing a category **archives** it — out of new entry, history intact, still shown in every period where it has a budget of more than zero or an expense, the current one included, never confirmed first and announced afterwards; an archived category is **brought back**, announced, by adding its name or by recording an expense against it — the second a **decision that overturned an earlier derivation**, which had assumed recording against a name adds it when in fact it is refused — so there are two routes back and still no separate un-archive act. The **assigning model** is now **built** too: assigning allowed in the current period and later ones and refused in a past one; zero accepted and moving nothing, unlike a zero transaction; refusals reported in a fixed order; and a **positive** assignment to an archived category bringing it back as a third route, while a negative or zero one leaves it archived. Decided for later increments but not built: an archived category's figure is not offered back when a period opens; and the full display rule, under which a category in use is shown in the current and later periods even without history, and a past period shows only categories with history; renaming deferred; and six Dutch **default categories** whose names are user-facing content rather than project vocabulary. Everything else holds as before — account-backed categories, the pool account, *Accumulated*, the end-of-period sweep, the expense account default, overdrawing, negative assignment against a *Budget* that floors at zero — including that an over-large one is clipped and the shortfall reported — and what a start day means in a month too short to contain it are all settled. Now also the **income model**: a required label where an expense's is optional, future-dating allowed where an expense's is not, *Unassigned* and *Left to assign* merged into one figure named *Unassigned*, *Over-assigned* named for its negative state, and net worth settled as a point-in-time figure that excludes expected income — so the two views disagree about it by design. All of that income model is now built, *Over-assigned* included, which became reachable once assigning was built ([§8.1](08-crosscutting-concepts.md)). **The user interface** is settled for the fifth increment and not built: it covers what the domain does and nothing more; it steps between periods, which is where the display rule gets built; the start day stays at the 1st for now; the start screen is the Overview, headed by a **ring** of budget-sized slices filled as far as spent plus a slice for *Unassigned*, with an empty grey outline when there is neither income nor budget, and one marker beside the negative figure for over budget and over-assigned (a **revision** of "plain negative figure, unremarked", which leaves how an overdraft is shown open again); category entry is free text with suggestions, so all three routes back stay reachable; no correction of entries, accepted for the demo; it starts with the default categories and keeps nothing; and it is in Dutch, with a **Dutch display terms** table kept separate from the *Dutch source terms*. Settled while its scenarios were written: an entry's date defaults to today and assigning to the period on screen; assigning is offered in a past period and refused; an expense, income or assignment landing in another period leaves the screen where it was and says where it went; no one-step way back to the current period; category rows show *Budget*, *Spent* and *Remaining*; categories and slices run largest *Budget* first, ties in order added (a brought-back category keeping its original place), *Unassigned* last going clockwise; expenses and incomes are two lists, each newest first; the Overview is laid out income left, plan middle, expenses right, as the stakeholder's wish; and a MoneyBud left open past a period boundary stays on the period it showed. Three scenario-writer assumptions and one consequence of that last rule are recorded as awaiting the scenario gate, not as decisions |

## Where this connects

Section 10's quality scenarios and the [Gherkin features](../../features/) describe different
things and should not be confused. Gherkin covers **functional** behaviour — what the user can do.
Section 10 covers **quality** attributes — how well, how fast, how safely.
