# 11. Risks and Technical Debt

**What belongs here:** Known technical risks and accumulated debt, stated plainly, ideally with
what could be done about each.

This section is only worth anything if it is honest. A risk section listing no real risks tells the
reader the document isn't maintained.

---

| Risk / debt | Impact | Mitigation |
|---|---|---|
| **Manual entry and accurate net worth pull against each other.** An accurate net worth requires every transaction to be recorded; requiring that is exactly the friction that makes people abandon budgeting apps. The app cannot detect a forgotten transaction, because nothing outside it knows what the truth is | High — this is the most likely cause of the product quietly becoming useless | Not solved. Options include letting balances be corrected by hand, or reconciling entered balances against calculated ones and reporting the difference. Bank import would largely remove it, but conflicts with local operation. **The first option was taken on 2026-09-27, and built the same day** ([§12](12-glossary.md), *Accounts and net worth*): a balance is worked out from its entries, and the user puts a wrong one right by typing the real balance, which MoneyBud records as a *balance correction*. Showing entered and calculated balances side by side was rejected. A balance correction takes in every entry dated before it, so a forgotten expense stops showing in the balance. **The second option is recovered for corrected accounts** (ruled and built the same day): the account's history shows each balance correction **with the new balance and the difference**, "Correctie — saldo € 1.000,00 (− € 23,40)". **The difference is recomputed, not fixed**: it is always what is still unexplained. Record the forgotten €23,40 expense, dated before the balance correction, and it shows € 0,00, while the balance stays €1.000. So it is a working reconciliation, not only a trace. As forgotten entries are found it shrinks, and at €0,00 the user knows he has found everything ([§12](12-glossary.md), *The accounts strip, and an account's history*). **What it still does not do**: it says how much is missing, not what. It is shown in the history, not on the Overview, and nothing prompts a look. It exists only for accounts the user corrects. Until the missing entry is found, the purpose side stays short by it, and nothing there reports it |
| **Two mechanisms will write the same account balance.** Once accounts exist, an *account-backed* category ([§12](12-glossary.md)) makes a balance move as a **side effect of a planning action**: assigning to Savings transfers real money into its backing account, and the end-of-period sweep does the same unprompted. Both movements now have a designated **source** as well — the *pool account* ([§12](12-glossary.md)) — so one everyday account is written automatically by every assignment to a backed category and by every sweep, which makes it the single balance most exposed to this. Meanwhile round 2 settles that the user can also edit a balance freely by hand. So a balance is authored from two directions — one automatic, one manual — and, as the row above records, nothing outside MoneyBud knows which is right. The failure is quiet: the user tops up savings in the bank app, MoneyBud transfers the same money again on assignment, and the balance is double-counted with nothing to contradict it. **A third route reaches a wrong balance from the other side.** An expense whose category is unbacked now *defaults* to the pool account rather than asking ([§12](12-glossary.md)), so an expense paid in **cash** and entered without overriding the account is deducted from the wrong place: the pool account reads low by money that never left it and the cash account reads high by money that did, and nothing outside MoneyBud will say so. Cash is the likely case precisely because nothing about it looks different at entry. This one is **known and accepted** — it was argued out before the default was taken, the override exists, and the decision saved on every expense was judged worth it ([§12](12-glossary.md), quality goal 2) — so it belongs here as a recognised cost, not as an unnoticed hole. **Since 2026-09-27 the hand edit is no longer a free overwrite** (settled, and built the same day): it records a *balance correction*, a dated statement of what the account really held that day, beside the entries ([§12](12-glossary.md), *Accounts and net worth*) | **High since the backing increment was built (2026-09-27)**, as this column said it would become. Medium before that; the text below is kept as written. **Accounts are in the code since 2026-09-27**, so the manual half and the third route are live. The first route, the automatic writer, is still **latent**: nothing moves money by itself yet. Becomes high the moment backing is built, because a wrong balance corrupts net worth, which is one of the two questions the app exists to answer ([§1.1](01-introduction-and-goals.md)). A hand edit also makes the two halves of the model disagree openly: *Accumulated* ([§12](12-glossary.md)) is computed purely from assignments and expenses, so it does not follow an edited backing account, and because backing is many-to-many the difference cannot be attributed to any one category. **The third route is no longer latent**: every expense is on an account, pre-filled with the pool account, so a cash expense left on the default writes a wrong balance. The automatic writer, the first route, stays latent until backing, the increment after. **Backing was settled with the stakeholder on 2026-09-27 and is not built** ([§12](12-glossary.md), *Backing and Accumulated*), so the automatic writer is now designed: an assignment to a backed category moves money from the pool account on the day of assigning or the period's first day if later; backing a category moves its unspent *Remaining* for the current period; and, since the stakeholder's revision the same day, **unbacking moves what is there for the category in its backing account back to the pool account, and re-pointing moves it to the new account**: what MoneyBud moved in for it, minus its expenses paid from that account (made exact in a follow-up). That is four automatic writers, not one. This row rises to high when they are built. **The rulings also make *Accumulated* and a backing account's balance differ on purpose**, which sharpens the "disagree openly" above: by money already in the account when it starts backing (ruled, and accepted with that cost), and by spending against a backed category put on another account (ruled in a follow-up: it lowers *Accumulated* and not the backing account). Because unbacking and re-pointing move what is there for the category in the account, not *Accumulated*, that second difference is **not** left behind: the backing account ends with nothing on the category's behalf, and the pool account exactly down by what it paid. A move **may overdraw** the account it leaves, when that account paid for something else, and that is ruled true: shown *Rood*, never blocked (§12, *Backing and Accumulated*, follow-ups). The amount moved and *Accumulated* can therefore differ, by design. A first version of the rulings let unbacking and backing again move the same money twice. The revision removed that. **Built on 2026-09-27** ([ADR 0009](../decisions/0009-movements-are-entries.md)): all four automatic writers are live, so the double count this row names, a top-up made in the bank app and again by MoneyBud on assignment, can now happen. **What still keeps it from being worse**: every automatic move is a visible row in both accounts' histories, naming its category, so a double count can be found and a balance correction puts the balance right | **Decided on 2026-09-27, before accounts were built, as this row asked, and built the same day** ([ADR 0008](../decisions/0008-balance-is-worked-out.md)). **No balance is stored anywhere**, in memory or in the file, and a cache of one was rejected as a second author inside MoneyBud. A balance is **derived** from the incomes, expenses and transfers on the account, never stored as a free number. A hand edit is an **adjustment**, a *balance correction*, not an overwrite, and entered and calculated balances are **not** shown side by side. A balance correction is a **dated assertion**: the balance the bank showed on the day it was typed, so every entry dated before it is already in it and only later entries move the balance ([§12](12-glossary.md), *A typed balance is what the bank said that day*). An account with no typed balance, like a first start's *Betaalrekening*, is the plain sum of its entries until first corrected. **What that leaves.** (1) **The double count is not prevented, only made repairable.** Once backing moves money by itself, a top-up also made in the bank app is still counted twice. A balance correction then puts the balance right, and its difference shows in the account's history, but *Accumulated* does not follow it, as the Impact column says. How the two halves meet is for the backing increment. [§12](12-glossary.md) files a related question there: what purpose, if any, a starting balance or balance correction carries (*A question for the backing increment*). **Answered on 2026-09-27: none.** Such money stays seen by location only, and *Accumulated* does not include it (*Money the user already had stays by location only*). So the halves are ruled to differ by it rather than made to meet. (2) **"One entry to re-point" is weaker than this row hoped.** Changing or re-pointing an entry dated before an account's latest balance correction does not change that account's balance, because the balance correction already took it in. So a mis-defaulted expense the user has corrected past no longer shows up in that account's balance, and re-pointing it moves only the account it goes to. In [§12](12-glossary.md)'s reading that is usually the right figure, since the corrected balance is the bank's. (3) **A transfer can change net worth** when one of its two accounts has a balance correction after its date and the other has not. **Ruled true, not a flaw** (2026-09-27): each account follows its own balance corrections, and net worth is their sum. Making the account easy to change after the fact still matters more than any warning at entry would: the account field is a list, pre-filled and visible, and a row names its account when that is not the pool account. That shows a cash expense recorded on the cash account. It does not show one left on the pool by mistake. **For the backing increment's plan** (rulings settled 2026-09-27): ADR 0008 expected backing to "write entries, not balances". The rulings make that harder than it sounds. **A movement for a later period has no destination until its day**, because it goes to whatever the category is backed by on that period's first day ([§12](12-glossary.md), *Planned money follows the backing on the day it moves*). So it cannot be written as a finished entry when it is assigned, unless the entry is rewritten whenever the backing changes first. The revision of unbacking adds moves whose amount is what is there for the category in the backing account on that day, itself a worked-out figure and a second one beside *Accumulated*, so they too must either be worked out or fixed when made. A follow-up fixes the amount moved at backing against later-recorded expenses, and §12 derives the same for unbacking and re-pointing, so all three are amounts fixed on their day while planned movements are not. The alternatives the documentation can see are to work movements out from the assignments and a dated record of each category's backing, which keeps "worked out, never stored", or to write each one on its day, which would be the first thing MoneyBud does *at* a period boundary rather than working out on request. Either is costly to reverse once data is real, and it touches the file format, so it is likely to need a record of its own at the plan gate. **Answered at the backing increment's plan gate, 2026-09-27, and built** ([ADR 0009](../decisions/0009-movements-are-entries.md)): the second alternative. **Every movement is a stored entry, written on the day the money moves**, and money planned for a later period is written by **settling**, the first time MoneyBud runs on or after that period's first day, before anything else is done, with the backing and pool account of that moment. So the automatic writers write entries, as ADR 0008 expected, and a balance is still their sum. Working movements out was rejected because the amounts fixed on their day would have had to be stored anyway. **What that leaves.** (4) **Settling trusts the clock.** Nothing can change while MoneyBud is closed, and that is what lets a late settling see the first day's backing. A clock turned back settles nothing and forgets nothing. **A clock set wrongly ahead**, though, would settle the periods up to that date with that day's backing and move the settled-through day forward for good. The movements would be dated in the future, so balances would not show them until their dates, but they would not follow a backing changed in between. Worse, once the clock is put right, **money assigned afterwards to a backed category in those periods would never move**, and *Opgebouwd* would not count it as planned, because those periods count as settled already. Low: it needs a wrong system date, and a movement that is missing is visible as a balance that did not change. Not guarded: the stakeholder has not been asked, and a guard would have to guess which clock is right. MoneyBud has no repair for it short of starting over; editing the file by hand would also have to remove the movements written ahead (5) **A refused act straight after a period began leaves the settled money unsaved** until the next change, because only an act that changes the ledger saves. Nothing is lost: the next start settles the kept data the same way, with the same result ([§6](06-runtime-view.md), *Settling*). Accepted as a build choice ([§12](12-glossary.md), *Backing: chosen in the build*) |

| **Money representation is settled in code and on disk, and its stored form is the part that will be expensive to change** (see [§8.2](08-crosscutting-concepts.md)). Settled: amounts are always a whole number of cents, refused at entry if finer, so nothing in MoneyBud ever rounds; in code an amount is a signed `Money` value type over a `long` of cents, transaction amounts are positive magnitudes with direction carried by the transaction type, and there is no currency field ([ADR 0003](../decisions/0003-money-representation.md)). **Since the persistence increment, how amounts are stored is settled and built too**: whole cents as JSON integers, read strictly, so a fraction of a cent or cents written as text make the file unreadable rather than rounded ([ADR 0007](../decisions/0007-keeping-the-ledger.md)). What remains is **the standing condition on the whole-cents rule**: it holds only while every amount is typed in rather than computed, and §8.2 lists what would reopen it — a split leftover, a percentage, interest, a bank import, a second currency. It now reaches the file as well, which has nowhere to put a fraction of a cent | Low **while the data is demo data**: the stakeholder ruled that a new version need not read an older one's demo data ([§12](12-glossary.md), *Demo data may not survive a new version*), so a wrong format costs a fresh start, not a migration. The format is version 1 and reads nothing older. **It is version 2 since the accounts increment, and refuses version 1** ([ADR 0008](../decisions/0008-balance-is-worked-out.md)). **It is version 3 since the backing increment, and refuses versions 1 and 2** ([ADR 0009](../decisions/0009-movements-are-entries.md)), which the stakeholder allowed although the "up to and including accounts" extension had run out: *"I dont mind starting over"*. It rises to medium at the **switch to real use**, from which data must be carried across versions: a stored representation is the part that is genuinely expensive to change once real data exists. The stakeholder has ruled that his saves may be dropped at least up to and including the accounts increment ([§12](12-glossary.md), *Real use before accounts*), so nothing before then has to plan around it | The code half and the storage half are decided and built. **The file names its format and version**, so a later format is met by "cannot read" rather than misread, and reading an older version can start there when the switch to real use makes it a requirement. A starting balance or balance correction may be negative, which `Money` already allows. The difference a balance correction shows in its history is one more subtraction. **Backing, built on 2026-09-27, does not reopen it either**, although it is the first feature that moves an amount MoneyBud worked out: a *Remaining*, or what is there for a category, both sums and differences of typed whole cents. Nothing is divided or split. Several backing accounts per category, if they ever split money between them, would reopen it ([§8.2](08-crosscutting-concepts.md)) |

That applies *Demo data may not survive a new version* for the first time. **Backing was settled on 2026-09-27, and built the same day** ([§12](12-glossary.md), *Backing and Accumulated*; [ADR 0009](../decisions/0009-movements-are-entries.md)). So a valid sweep destination can now exist, but the sweep is the next increment, and the vanishing money stays accepted until then. The file format is version 3, and version 2 is refused as well. Settling, which writes a period's planned money when it begins, is the step the sweep is meant to use at a period's end. One ruling reaches the sweep ahead of time. As first ruled, a category's earlier money stayed in its backing account after unbacking, so it was not on the pool account the sweep will collect from. **The stakeholder revised that the same day**: unbacking returns it to the pool account, so the sweep's assumption holds. The part from earlier periods returns with no purpose, in no period's *Unassigned*, and so is not something a sweep of *Unassigned* and *Leftovers* would collect either |
| **All of MoneyBud's data is one file, which MoneyBud never copies.** Built 2026-09-26: `moneybud.json`, in the user's local application data, with backing up left to the user outside MoneyBud, and its location written only in the README, never shown by MoneyBud ([§12](12-glossary.md), *Backing up is the user's business*, *Where the data is, is written in the README*; [§7](07-deployment-view.md)). A damaged file is met by saying so, touching nothing and closing, which protects what is there but recovers nothing. **MoneyBud's own writing is ruled out as a cause of that damage**: an interrupted save, by a crash or a power cut, must leave the previous save intact, losing at most the change being saved ([§12](12-glossary.md), *An interrupted save never damages the previous one*). **Built** as a temporary file, flushed to the disk, then renamed over the data file ([ADR 0007](../decisions/0007-keeping-the-ledger.md)). That removes the likeliest way a single file with no copies loses its whole history. **What holds it is the file system's rename**, and it was checked by unit tests and a scenario that rebuild the state a cut-off save leaves, not by cutting the power during a real save. It does not reach a failing disk, a deleted profile or damage from outside MoneyBud. **A failed save adds a smaller loss**: MoneyBud says so on the save line, keeps it there, retries once a minute and after every change, and makes one last attempt on closing. Closing before any save succeeds loses the changes since, accepted by the stakeholder ([§12](12-glossary.md), *When a save fails, MoneyBud says so and keeps going*). A disk failure, a deleted profile or a damaged file with no backup of the user's own is the whole history gone, and nothing inside MoneyBud reminds anyone that a backup is needed | Low while the data is demo data, which the stakeholder has ruled may be thrown away, at least up to and including the accounts increment. Rises to high once the data is real: the history is the product, and net worth and a period's figures depend on every entry being there | Partly mitigated, and built: an interrupted save cannot damage the previous one, which is the one cause inside MoneyBud's reach. **Backing up is made as easy as the rulings allow**: it is copying one file, which is plain JSON and so can be checked by opening it, and which a save replaces whole rather than rewrites in place ([§7](07-deployment-view.md)). The rest is accepted by the stakeholder's ruling: backing up is not MoneyBud's job. He was offered keeping earlier copies and declined. The mitigation is outside MoneyBud: a backup of the user's own, of a file whose location the README states. If he later wants MoneyBud to help, the declined option is recorded in §12 |
